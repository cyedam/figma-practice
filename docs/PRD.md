# 수원문화재단 통합 온라인접수 개선 PRD

> 작성 근거: 현황표, 문제기록표, 핵심 가설, 사용자 여정지도(As-Is/To-Be), 개선 내용 메모
> 표기 규칙: 제공 자료에 근거가 없는 항목은 **"추가 확인 필요"** 로 표시함

---

## 1. 문서 개요 (Document Overview)

### 1.1 프로젝트 목적
문화 프로그램을 검색하고 신청하려는 이용자가 **통합 온라인접수**에서 신청 과업을 중도 이탈 없이 완수하도록, 신청 처리 및 오류 제어 과정을 개선한다.

### 1.2 대상 서비스 현황

| 구분 | 내용 |
| --- | --- |
| 기관 | 수원문화재단 |
| 주요 이용자 | 문화 프로그램을 검색하고 신청하려는 사용자 |
| 분석 과업 | 온라인 접수 |
| 과업 경로 | 메인 → 열린시설 → 통합 온라인접수 (메인에서 2회 이동) |
| 과업 단계 | 10개: 안내, 교육, 체험, 시설물대관, 수원전통문화관, 문화관광해설, 행궁동왕의골목여행해설, 근대여행골목길해설투어, 복합문화공간111cm대관, 기타 |
| 도움 수단 | 검색창, 문의처 |

### 1.3 목표
- **핵심 목표**: 1회 진입 내 최종 신청 완수
  - 성공 기준: 제출 직전 '확인·확정' 모달에서 입력 정보를 최종 재검토하여, 오입력으로 인한 취소·재작성 없이 첫 시도만으로 신청 제출에 성공함.
- **핵심 가설**: 작성 중 데이터 손실을 원천 차단하고 오류 복구 경로를 명확히 제시하면, 신청 과업 완수율(Task Completion Rate)이 높아지고 중도 이탈률이 낮아진다.

### 1.4 개선 우선순위

| 우선순위 | 테마 | 주요 개선 | 우선순위 부여 이유 |
| --- | --- | --- | --- |
| P1 | 테마 3. 신청 과업 처리 및 오류 제어 | 제출 전 '확인·확정' 모달, 작성 내용 파기 방지 경고 모달, 인라인 오류 메시지 배치 및 버튼 위계 분리 | 이용자의 최종 목표 달성을 직접 막는 치명적 과업 차단 요소 |
| P2 | 테마 2. 입력 폼 및 본인 인증 편의성 | CAPTCHA 외 대체 인증 수단 보장, 비밀번호 사전 규칙 안내 및 찾기/재설정, 복사·붙여넣기 허용 및 표시 토글 | 장애인·고령자의 이용 단절 방지 및 KWCAG 2.2 지침 준수 |
| P3 | 테마 4. 결과 조회 및 시스템 일관성 | 완료 안내 문구와 실제 조회 로직 일치, 접수번호 기반 조회 활용성 확보, 불필요한 드롭다운 UI 정돈 | 제출 후 조회 단계의 안내-시스템 불일치 및 혼란 해소 |
| P4 | 테마 1. 정보 탐색 및 안내 신뢰성 | 카테고리 바로가기(탭) 및 접수중/전체 건수 표기, 0건 항목 흐리게 표시 및 후순위 배치, 검색 결과 건수·키워드 강조, 최신 가이드 업데이트 | 스크롤과 헛걸음을 줄이는 탐색 편의성 향상 항목으로 순차 추진 |

> 본 문서의 기능 요구사항(4장)은 P4(프로그램 조회)부터 P1~P3 및 대체 인증수단 추가 건까지 포함함.

## 2. 타겟 페르소나 (Target Persona)

### 김영숙 님 (68세, 디지털에 서툰 이용자)

| 항목 | 내용 |
| --- | --- |
| 상황 | 온라인으로 '손자와 함께 할' 문화 프로그램을 찾아 신청서를 작성함 |
| 겪고 있던 불편 | 알림창을 닫은 뒤 오류 칸이 표시되지 않아 한참 찾아 헤맴. 실수로 '취소'를 누르면 경고 없이 목록으로 이동하며 작성 내용이 모두 삭제됨. 이로 인해 신청을 포기함. 제출 후 전화번호 오타를 발견해도 온라인에서 수정·취소할 수 없어 전화로 문의해야 함 |
| 기대(여정지도 To-Be 기준) | 오류 칸 하단에 메시지가 남아 바로 고칠 수 있을 것. 실수로 버튼을 눌러도 '작성 내용이 사라집니다' 경고가 떠서 안심하고 작성을 마칠 수 있을 것. 제출 직전 확인 화면에서 입력한 정보를 다시 확인하고 제출할 수 있어, 접수 후 전화로 정정하지 않아도 될 것 |

> 추가 확인 필요: 페르소나의 조사 방법(인터뷰·설문 등)과 표본 근거는 제공 자료에 없음.

## 3. 핵심 사용자 여정 (Core User Journey)

### 3.1 개선 후(To-Be) 흐름 요약

```
[1 신청서 작성] → [2 입력 오류 정정] → [3 취소/초기화 조작] → [4 제출 및 확정] → [5 제출 후 확인]
```

| 단계 | 이용자 행동 | 개선 기능 |
| --- | --- | --- |
| 1. 신청서 작성 | 인라인 지시사항에 따라 입력 | 입력 규칙 사전 안내(예: 숫자 4자리), 제출(주요색)·취소(윤곽선) 버튼 위계 분리 |
| 2. 입력 오류 정정 | 오류 발생 시 해당 필드로 초점이 이동해 정정 | 입력 필드 하단 인라인 오류 메시지 지속 노출(aria-live) |
| 3. 취소/초기화 조작 | 실수로 '목록으로'를 눌러도 경고를 확인하고 작성 계속 | 버튼 레이블 '목록으로', 작성 내용 파기 경고 모달 |
| 4. 제출 및 확정 | 확인·확정 모달에서 입력 정보를 재검토하고 제출 | 제출 직전 확인·확정 모달(신청자명, 연락처, 수강과목 등 재확인) |
| 5. 제출 후 확인 | 신청 완료 화면 및 '내 신청내역'에서 결과 확인 | 1회 진입 내 접수 완료, 완료 안내와 실제 조회 로직 일치 |

### 3.2 개선 전(As-Is) 대비 핵심 페인포인트

| 단계 | As-Is 페인포인트 |
| --- | --- |
| 1 | 비밀번호 규칙 사전 안내 없음, 버튼 시각적 위계 미흡 |
| 2 | 알림창을 닫은 후 빨간색 인라인 오류 문구가 남지 않음 |
| 3 | 경고창 없이 즉시 목록으로 이동, 작성 데이터 전량 삭제 |
| 4 | 확인·확정 모달 없이 즉시 접수 완료, 오입력 검토 기회 없음 |
| 5 | 전화번호 오타 발견 시 온라인 수정·취소 불가, 전화 민원 발생 |

## 4. 기능 요구사항 (Functional Requirements)

> 세부 디자인 스펙(색상, 크기 등)은 정해지지 않았으며, **세부 스펙은 다음 단계에서 확정 예정**임. 아래는 "어떤 기능을 어떻게 개선하는가" 수준으로 기술함.

### FR-1. 프로그램 조회 (P4)
- 카테고리 바로가기(탭)를 제공하고, 각 카테고리에 접수중/전체 건수를 표기하여 원하는 분류로 바로 이동할 수 있게 한다.
- 접수 가능한 프로그램이 0건인 카테고리는 흐리게(Dimmed) 표시하고 후순위로 배치한다.
- 검색 결과에 검색 결과 건수를 표시하고, 일치한 키워드를 강조한다.
- 접수 가이드를 최신 내용으로 업데이트한다.
- 0건 항목의 선택 가능 여부, 검색 결과 없음 화면의 구성, 가이드 갱신 주기와 담당: 추가 확인 필요.

### FR-2. 제출 전 확인·확정 (P1)
- 제출 버튼 선택 시 바로 접수하지 않고, 입력 정보(신청자명, 연락처, 수강과목 등)를 보여 주는 확인·확정 모달을 먼저 표시한다.
- 이용자는 모달에서 정보를 확인한 뒤 최종 제출하거나, 작성 화면으로 돌아가 수정할 수 있다.
- 표시 항목의 최종 범위: 추가 확인 필요.

### FR-3. 작성 내용 파기 방지 (P1)
- 작성 중 '목록으로'(기존 '취소')를 선택하면 즉시 이동하지 않고 경고 모달을 표시한다.
- 경고 모달에는 작성 내용이 사라진다는 결과를 알리고, 작성을 계속하거나 나갈 수 있는 선택지를 제공한다.
- 취소 버튼 레이블을 '목록으로'로 변경한다.

### FR-4. 입력 오류 처리 (P1)
- 필수 항목 누락 등 오류 시, 알림창을 닫으면 오류 필드로 초점이 이동한다.
- 오류 메시지는 해당 입력 필드 하단에 오류가 해소될 때까지 유지한다.
- 화면 낭독기가 오류를 즉시 읽을 수 있도록 aria-live를 적용한다.
- 오류가 발생해도 이미 입력한 값은 보존한다(여정지도 To-Be의 '데이터 보존' 기준).
- 오류 유형별 문구와 검증 규칙: 추가 확인 필요.

### FR-5. 버튼 위계 분리 (P1)
- 제출 버튼은 주요색, 취소(목록으로) 버튼은 윤곽선 형태로 구분한다.

### FR-6. 입력 폼 및 비밀번호 (P2)
- 비밀번호 입력 규칙(예: 숫자 4자리)을 입력 전에 안내한다.
- 비밀번호 표시/숨김 토글을 제공한다.
- 복사·붙여넣기를 허용한다.
- 비밀번호 찾기/재설정 경로를 제공한다. 재설정 방식과 본인 확인 절차: 추가 확인 필요.

### FR-7. 대체 인증 수단 (P2)
- 대체 인증수단이 미비하여 추가한다(개선 내용 메모 기준). CAPTCHA 외 대체 인증 수단을 보장하여 장애인·고령자의 이용 단절을 막는다.
- 대체 인증수단의 종류와 방식: 추가 확인 필요.

### FR-8. 결과 조회 일관성 (P3)
- 신청 완료 화면의 안내 문구를 실제 조회 로직과 일치시킨다.
- 접수번호 기반 조회 활용성을 확보한다.
- 불필요한 드롭다운 UI를 정돈한다.
- 접수번호 조회의 구현 가능 여부 및 범위: 추가 확인 필요.

### 예외 처리 정리

| 상황 | 처리 |
| --- | --- |
| 필수 항목 누락 | 알림 후 초점 이동, 필드 하단 오류 문구 유지, 입력값 보존 |
| 작성 중 이탈(목록으로) | 파기 경고 모달 표시, 확인 전에는 이동하지 않음 |
| 제출 직전 오입력 | 확인·확정 모달에서 정정 후 제출 |
| 제출 후 오입력 발견 | 개선 후 목표는 0건. 발생 시 처리 방안: 추가 확인 필요 |

## 5. UI/UX 및 정책 요구사항 (UI/UX & Policy Requirements)

### 5.1 준수 기준
- 웹 접근성: KWCAG 2.2 (여정지도 기준 KWCAG 7.3.1 오류 정정, 7.3.2 지시사항 항목 해당)
- 사용성 원칙: 휴리스틱 #1 시스템 상태 가시성, #3 사용자 통제와 자유, #5 오류 예방, #9 오류 복구 지원
- 신청 과업 UI/UX 가이드라인: 확인·확정 단계 및 신청 결과 안내

### 5.2 공공언어 가이드라인
- 버튼 레이블은 '목록으로'처럼 이동 결과가 드러나는 말로 쓴다.
- 오류 문구는 무엇이 잘못되었는지와 어떻게 고치는지를 함께 알린다.
- 입력 규칙은 입력 전에 안내한다(예: 숫자 4자리).
- 공공언어 세부 문구 기준(문장 길이, 용어 통일 등): 추가 확인 필요.

### 5.3 시각적 우선순위
- 주요 행동(제출)은 주요색, 보조 행동(목록으로)은 윤곽선으로 구분한다.
- 오류 표시는 필드 하단에 지속 노출한다(여정지도 기준 빨간색 인라인 오류 문구).
- 색만으로 의미를 전달하지 않는 방안(아이콘, 문구 병행): 추가 확인 필요.

### 5.4 레이아웃 규칙
- 오류 메시지는 해당 입력 필드 바로 아래에 배치한다.
- 확인·확정 모달과 파기 경고 모달은 이용자가 현재 작업을 잃지 않는 선택지를 기본으로 한다.
- 그 외 레이아웃 세부 규칙: **세부 스펙은 다음 단계에서 확정 예정**

### 5.5 반응형

#### 1. 브레이크포인트
- 모바일: ~767px
- 태블릿: 768px ~ 1439px
- 데스크탑: 1440px ~

#### 2. 작성 방식
- 모바일 우선(Mobile First)으로 작성한다.
- 미디어쿼리는 min-width 기준으로 통일한다. (기본 스타일 = 모바일, 768px 이상 = 태블릿, 1440px 이상 = 데스크탑)
- 위 브레이크포인트 3개만 사용하고, 임의의 px 값으로 미디어쿼리를 추가하지 않는다.

#### 3. 단위 규칙
- 레이아웃 너비는 상대단위(%)를 사용하고, 고정 px 너비는 지양한다.
- em 단위는 사용하지 않는다.
- 폰트 크기와 간격(padding, margin, gap)은 rem을 사용한다.

#### 4. 터치 영역·가독성
- 터치 가능한 요소(버튼, 링크, 입력창 등)는 모바일에서 누르기 편한 최소 크기를 확보한다.
- 모바일에서도 읽기 편한 최소 폰트 크기를 유지한다.
- 구체적인 수치는 Figma 디자인 기준으로 구현 단계에서 확정한다.

#### 5. 상세 디자인 전달 방식
- 반응형 상세 디자인(컨테이너 최대 너비, 좌우 여백, 컴포넌트별 변화 등)은 구현 단계에서 사이즈별 Figma 링크로 전달한다.
- 이 값들은 PRD에서 확정하지 않고 "구현 단계에서 정의"로 표기한다.
